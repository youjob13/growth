## Cookie Injection Protection

1. Использование *cookies prefix* для защиты от cookie injection через поддомены. Префикс это специальное начало имени cookie, которое говорит браузеру "эта cookie обладает расширенными гарантиями безопасности".
**Браузер отклонит cookie, если хоть одно условие не выполнено.**

### `__Host-`
```http
Set-Cookie: __Host-session=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
```
Жёсткие требования браузера:
- Должна иметь флаг Secure (только HTTPS).
- Должна иметь Path=/ (нельзя ограничить путь).
- Не должна иметь атрибут Domain (только текущий домен, без поддоменов).

### `__Secure-`
```http
Set-Cookie: __Secure-token=xyz789; Secure; SameSite=Strict
```
Требования:
- Только флаг Secure (обязателен).
- Остальное — на усмотрение.

Пример:
У тебя есть основной домен *bank.ru* и поддомен *cdn.bank.ru* (или *evil.bank.ru* — если захвачен злоумышленником).
Злоумышленник может установить cookie с `Domain=.bank.ru` на любой поддомен (например, *evil.bank.ru*).
Без префикса: браузер примет эту cookie для *bank.ru* и всех поддоменов.

С префиксом __Host-:
Браузер откажется принимать cookie, если она пришла с другого поддомена или с Domain атрибутом.
Даже если *evil.bank.ru* пытается установить `__Host-session=malicious` — браузер проигнорирует её, потому что она нарушает правила префикса.

## Stolen session cookie Protection

1. При создании сессии запоминать (IP, User-Agent, Accept-Language, Date, Accept, Accept-Encoding, Sec-ch-*)
2. Cравнивать при каждом следующем запросе.
3. Если есть большие различия - требовать ре-логин

Поверхностное сравнение может приводить к плохому UX (False positive). 
Например пользователь путешествует, или переподключается с мобильного интернета на WIFI

## Brute-force session guessing attacks Protection

- Session ID должны иметь как минимум **64 бита** параметр рандомности/непредсказуемости (entropy) === 16 шестнадцатеричные символом. Session ID с 64 битами энтропии может иметь 2^64 возможных значений
