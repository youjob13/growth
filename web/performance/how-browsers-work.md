## Как работает браузер

### 1. Навигация - первый этап при загрузке приложения.

a) DNS запрос - первый шаг навигации к странице - поиск места, откуда запрашивать данные. Если вы никогда ранее не были на сайте, произойдет поиск DNS записи (затем DNS запись временно закешируется на устройстве и при следующем входе поиска по DNS не произойдет)
DNS запрос должен быть выполнен для каждого уникального имени хоста (если шрифты, картинки, скрипты и т.д. находятся на разных доменах, DNS запрос будет осуществлён для каждого из них)

#### DNS-prefetch
Попытка определить IP адрес по имени домена до того, как ресурс с этого домена будет фактически запрошен. Это может быть ссылка, по которой, вероятно, перейдёт пользователь.
Используйте **dns-prefetch** в случаях, когда в вашем приложении используются ссылки на домены, отличные от основного домена приложения.

#### Preconnect
Устанавливает соединение к нужному серверу. Включает в себя DNS resolution, TCP handshake, TLS negotiation)

Используйте `dns-prefetch` вместе с `preconnect` для запросов на сторонние домены.

b) TCP handshake
После получения IP адреса источника данных, браузер начинает установку соединения к этому серверу при помощи TCP three-way handshake.

c) TLS Negotiation 
Для установки безопасных соединений с использование HTTPS требуется еще одно рукопожатие. На этом шаге определяется, какой шифр будет использоваться для шифрования соединения, удостоверяется надёжность сервера и устанавливается безопасное соединени.

### 2. Ответ на запрос / Инициирующий HTTP Get request
Чаще всего запрашивается HTML файл. В момент, когда сервер получает запрос, он начинает ответ с посылки заголовков ответа и содержимым HTML-файла.
Этот ответ содержит в себе первый байт полученных данных (Time to First Byte, TTFB) - время между моментом, когда пользователь отправил запрос и моментом получения первого пакета данных HTML. Первый пакет содержит 14kb.

#### TCP медленный старт / правило 14kb
Объем первого пакета данных - всегда 14kb. Алгоритм балансирует скорость соединения. Размер передаваемых данных постепенно увеличивается, пока не будет определена максимальная ширина канала. Каждый следующий пакет, отправленный сервером, увеличивается в размере в два раза.
14kb -> 28kb - 56kb.

#### Контроль переполнения
Любое соединение имеет аппаратные и сетевый ограничения. Если сервер отправит слишком много пакетов за раз - они могут быть отброшены. Для избежания этих проблем, браузер реагирует на получение пакетов и подтверждает, что он получает их. ACK (Acknowledgements). 
Если браузер не отправит ACK, сервер зарегистрирует, что какие-то пакеты не дошли и пошлёт их заново, что приведёт к лишней работе сервера и дополнительной нагрузке на сеть 

### 3. Парсинг
Как только браузер получает кусок данных, он сразу же начинает обрабатывать получаемую информацию.

#### 3.1 Преобразует данные в DOM и CSSOM.
##### DOM - внутреннее представление разметки HTML. Браузер предоставляет доступ к манипуляции объектами этой разметки через JavaScript API. Построение DOM **инкрементально**.
HTML -> токены -> nodes -> DOM Tree.

Node - вся необходимая информация об HTML-элементе.

##### Неблокирующие ресурсы - загружаются параллельно с парсингом HMTL
- Изображения
- Видео
- CSS не блокирует парсер HTML, но блокирует рендеринг (CSS может косвенно блокировать парсинг HTML, в случаях если есть синхронный script)
- Шрифты

##### Блокирующие ресурсы - парсер останавливает обработку HTML до полной загрузки и выполнения ресурса
- script (без async или defer) - останавливает обработку HTML до завершения загрузки скрипта. Парсер останавливается -> управление передаётся JS-движку -> скрипт скачивается и выполняется -> парсер продолжает разбор.

| этап | синхронный скрипт | async | defer / type="module" |
|------|-------------------|-------|-----------------------|
| Скачивание | Блокирует парсинг | Не блокирует / параллельно | Не блокирует / параллельно |
| Выполнение | Блокирует парсинг | Блокирует парсинг | Не блокирует / выполняется после построение DOM (перед DOMContentLoaded) |
| Порядок выполнения скриптов | Строго по документу | Не гарантирован | Строго по документу |

- CSS блокирует выполнение JavaScript (если парсер встречает script, он должен дождаться загрузки всех уже объявленных (выше по html документу) стилей)

##### Сканер предзагрузки
Т.к. построение DOM узкое место в производительности (занимает весь поток процесса) был создан сканер предзагрузки.
Он обрабатывает доступное содержимое документа и запрашивает высокоприоритетные ресурсы (CSS, JavaScript и шрифты). Благодаря этому сканеру нам не нужно ждать, пока парсер дойдёт до конкретного места, где вызывается ресурс.
Он запрашивает и получает эти данные заранее, в фоновом режиме, так что когда основной поток HTML-парсера доходит до запроса ресурсов, высока вероятность, что ресурс уже запрошен или находится в процессе загрузки.
Ожидание получение CSS не блокирует парсинг HTML, но блокирует JavaScript, потому что JavaScript часто используется для выборки nodes документа по CSS-селекторам.

##### CSSOM - стили страницы. CSSOM формируется **НЕ инкрементально**. 
CSS блокирует рендер: браузер блокирует рендеринг, потому что правила могут быть перезаписаны, а значит необходимо дождаться построения CSSOM, чтобы убедиться в отсутствии дополнительных переопределений.
Парсер преобразует токены в nodes, вложенные узлы наследуют стили от родительских.
Наименее специфичные селекторы работают быстрее.

##### Остальные процессы

- **Компиляция JavaScript** - после загрузки должен быть интерпретирован, скомпилирован, обработан и исполнен. Скрипты преобразовываются в AST (абстрактное синтаксическое дерево)
- **Построение дерева доступности** - используется устройствами-помощниками для понимания и интерпретирования контента (AOM). Семантическая версия DOM.

#### 3.2 Строит Render Tree
Render Tree охватывает сразу и содержимое страницы и стили: DOM и CSSOM комбинируется в одно дерево, браузер проверяет каждый node DOM начиная с root и определяет, какие CSS правила нужно присоединить к этому node.
Render Tree охватывает только видимое содержимоей. head не включена в дерево, node с `display:none` не включается в дерево

#### 3.3 Layout / Reflow
Layout определяет, где и как на странице будут спозиционированы элементы и каковы связи между ними.
Блочные элементы по умолчанию имеют ширину 100% от ширины их родителя.
Мета тэг viewport, определяет ширину видимой области и влияет на компоновку. (по умолчанию 960px)

#### 3.4 Paint
Отрисовка пикселей на экране (First Meaningful Paint случается здесь при первой отрисовке). При первичной загрузке документа весь экран будет отрисован. После этого будут перерисовываться только необходимые к обновлению части экрана, так как браузер старается оптимизировать процесс отрисовки.

#### 3.5 Composition
Отрисовка может разбить элементы в дереве рендера на слои. Чтобы ускорить их рендер, браузер может перенести отрисовку разных слоёв на GPU (вместо основного потока CPU). Для переноски на GPU используйте теги: <video>, <canvas>, css-property `opacity`, `transform`, `will-change`..
Слои улучшают производительность, но с точки зрения управления памяти они неэффективны.
Освобождает основной поток, позволяя отрисовывать содержимое экрана на графическом процессоре.

Reflow запускает re-paint и re-composition. Если мы заранее определили размер изображения, re-paint не будет необходим и в этом случае только тот слой, который должен быть перерисован - будет перерисован.

### 4. Интерактивность (Time to Interactive, TTI)
Браузер начинает обработку отложенных скриптов. Во время этого браузер не может обрабатывать события прокрутки, нажатия и др. 
TTI - показатель того, как много времени проходит между самым первым сетевым запросом и моментом, когда страница становится интерактивной
