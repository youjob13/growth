## CSRF

Cross-Site Request Forgery атаки случаются, когда враждебный код/сайт/email/blog прикидывается авторизованным пользователем и пытается выполнить нежелательные действия на доверенной стороне. Если целевой пользователь авторизован на сайте, незащищенные целевые сайты не могут отличить авторизованный запрос от поддельные запросы. 
Т.к. запросы браузера автоматически включают все cookies, включая session cookies. Эта атака работает только при отсутствии надлежащей авторизации.

## Методы защиты от CSRF

### 1. Не реализовывать state-changing операции в приложении через безопасные методы (GET, HEAD, OPTIONS, TRACE)
### 2. CSRF токены
Суть CSRF токена доказать, что запрос инициирован НАШИМ клиентом (сайтом), а не злым сторонним сайтом.

#### Два способа реализации
a) Syncronized Token Pattern (STP) - Сервер - источник правды
Сервер генерирует токен, хранит его в сессии (на сервере) и отдает клиенту (например в ответе на GET-запрос). Клиент обязан вернуть его обратно в каждом CSRF-чувствительном запросе. Сервер сверяет присланный токен с тем, что в сессии.
1. `GET /form` -> Сервер создаёт токен `ABC123`, кладёт в сессию `session.csrfToken="ABC123"`, возвращает в HTML или JSON
2. `POST /action`-> Клиент отправляет `csrf=ABC123`. Сервер сравнивает `request.csrf` с `session.csrfToken`. Совпало -> запрос валиден.

Плюсы:
- Надёжность: злоумышленник физически не может узнать токен (он не хранится в cookie, а на сервере)
- Не зависит от политики cookie (можно использовать даже без SameSite) 
Минусы:
- Каждый запрос требует чтения токена из сессии (лишний I/O)
- Stateful (хранит состояние на сервере) - нагрузка на память/хранилище

b) Double Submit Cookie (DSC) - Клиент носит секрет сам
Сервер не хранит токен. Вместо этого он записывает токен в cookie и также ожидает его в теле запроса (или заголовке). Сервер просто проверяет: совпадает ли значение из cookie со значением в запросе. Если да - значит, запрос пришел с нашего домена, потому что злоумышленник не может прочитать cookie (Same-Origin Policy) и не может подделать оба значения.
1. `GET /form` -> Сервер генерирует токен `XYZ789`, отправляет его в `Set-Cokie: csrf=XYZ789` и в тело скрытого поля формы
2. `POST /action` -> Браузер автоматически отправит cookie `csrf=XYZ789` (по SameSite) + клиент включит токен в тело запроса. Сервер проверяет токены.

Плюсы:
- Stateless - идуально для микросервисов и масштабирования (нет общих хранилищ)
- Не требует чтения сессии
Минусы:
- Теоретическая уязвимость: если злоумышленник может заразить поддомен, он может установить свою cookie на родительский домен. Тогда оба значения в его власти.
- Требует чтобы cookie не имела флаг HTTPonly (чтобы JS мог её прочитать и подставить в заголовки)

### 3. Sec-Fetch заголовки (или фолбек сравнение source origin & target origin)
Sec-Fetch metadata заголовки дают дополнительную информацию о контексте, в котором был сделан HTTP запрос. Сервер может использовать эти заголовки (в частности Sec-Fetch-Site) как легкий и надежный способ блокировать очевидные cross-site запросы.

#### Использование стандартных заголовков для верификации origin
1. Определить origin, с которого пришел запрос - `source origin` (Origin or Referer header)
Надежность этих заголовков подтверждается фактом, что они не могут быть изменены программно т.к. они попадают в категорию **[запрещенных заголовков](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_header_name)**

2. Определить origin, на который запрос отправлен - `target origin`.
Не всегда возможно определить target origin (из url), потому что часто сервер находится за одним и более прокси. Это означает, что оригинальный URL может отличаться от URL, которое получил сервер.
Если мы используем прокси то:
- Если это наше приложение, мы значем target origin и можем хранить его в env переменной
- Использовать host заголовок (может быть подменен прокси сервером)
- Использовать X-Forwarded-Host заголовок. Reverse proxy может сохранить оригинальный host в этом заголовке. Использовать только на доверенных прокси!

На стороне сервера мы валидируем, что оба совпадают (same origin).
Если origins не совпадают, мы отклоняем запрос.

### 4. SameSite (Cookie attribute) - защищает от CSRF атак, ограничивая отправку cookie в зависимотси от того, откуда пришёл запрос. Помогает решить отправлять ли cookie с кросс-сайтовыми запросами (кроме CSRF методов подверженых риску e.g. POST, они запрещены)
   a) Lax - cookie отправляется при переходе по ссылке (навигации верхнего уровня) с другого сайта. Но не отправляется при фоновых запросах (fetch, XHR, загрузка изображений, iframe).
   b) Strict - cookie никогда не отправляется с запросами, инициированными с другого сайта, во всех cross-site browsing context (tab, window, popup, web application, frame or iframe). Даже если пользователь кликает по обычной ссылке.
   c) None

#### Ограничения SameSite
- Lax блокирует только небезопасные методы (POST, PUT, DELETE etc.)
- SameSite ограничен регистрируемым доменом. Cookie добавленые на `app.example.com` с любым значением SameSite будут рассмотрены как "same-site", когда реквест выполняется из `anything.example.com` (multi-tenant SaaS on a shared parent domain)
- Top-level navigation and window-opening tricks - злоумышленник, имеющий возможность выполнять top-level навигацию или открыть новое окно (включая, window.open, prerendering hints или crafted link) может сгенерировать реквест, который браузер расценит как SameSite=Strict
